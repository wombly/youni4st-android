# Интеграция с существующим сервером

## Подключено в Android-клиенте

`POST /api/chat`: JSON `message`, `history`; ответ `reply`. Клиент не содержит ключа AI-провайдера, токена Telegram или webhook CRM. Запрос выполняется только по действию пользователя. Ошибки и пустые ответы отображаются как ошибки, доступен повтор без дублирования последнего сообщения.

## Найдено в серверном коде, не подключено автоматически

- `GET/POST /api/sync/{telegram_id}` — хранение произвольных данных по Telegram ID.
- `GET /api/status/{lead_id}`, `POST /api/status/batch` — статусы заявок.
- `POST /api/subscribe` — подписка на проверку CRM и уведомления.
- `POST /api/pdf/upload`, `GET /api/pdf/{token}/{filename}` — временная выдача PDF.
- Telegram и Bitrix webhook/admin routes.

Эти методы не заменяют авторизацию пользователя и не создают новый отклик. Android-приложение не придумывает Telegram ID и не выдаёт локальную запись за отправленную заявку.

## Необходимые изменения перед рабочей интеграцией

1. Выбрать вход для Android: телефон, email, Google или подтверждённая привязка Telegram. Сервер должен проверять токен и права на профиль.
2. Добавить защищённые методы профиля/резюме и синхронизации избранного, привязанные к авторизованному пользователю.
3. Добавить API создания отклика и записи на консультацию. Сервер отвечает идентификатором и подтверждённым статусом; повторные запросы должны быть идемпотентны.
4. Отдать каталоги через API с устойчивыми идентификаторами и датой обновления. В этой версии идентификаторы локальные (`kind:index`); перед перестановкой элементов нужен переход на серверные ID и миграция избранного.
5. Подключить FCM для Android-уведомлений, если они нужны.

## Замечания к текущему backend

В `main.py` обнаружены значения секретов непосредственно в коде. Их необходимо отозвать/заменить у соответствующих провайдеров и хранить только в переменных окружения. Сами значения здесь не приводятся и в Android-приложение не переносились.

Методы синхронизации в изученном коде обращаются к профилю по переданному Telegram ID без проверки токена владельца. Административные методы регистрации webhook также требуют защиты перед подключением публичного мобильного клиента.

В обработчике скачивания PDF используется `debugPrint`, который не определён в Python-файле. Перед подключением PDF необходимо исправить эту ошибку на сервере и проверить доступ/срок жизни файла.

Серверный репозиторий в рамках начальной Android-версии не изменялся; рассылки, подписки и внешние CRM-записи не создавались.

## Изменения Android 0.2.0

Клиент Firebase Authentication реализован для телефона, Google и E-mail, но конфигурация проекта Firebase ещё не предоставлена. Синхронизация профиля с сервером не добавлялась. Новый клиент отправки отклика описан в `APPLICATIONS_API.md`: без настроенного HTTPS endpoint отправка недоступна. Наставники теперь открываются по `profile_url`, запрос на запись не создаётся. PDF формируется на устройстве, серверный метод PDF не используется.

В каталоги добавлены явные постоянные `id`, совпадающие с прежними `kind:index`; их следует сохранять при перестановке записей. Существующее избранное и локальные черновики не удаляются. Старые черновики доступны из профиля.
