# API приёма откликов · контракт Android 0.2.0

Существующий backend не предоставляет нужного защищённого метода создания отклика. Клиент реализован в `ApplicationApi.kt`; сервер по этому контракту ещё требуется создать и подключить. Один URL `applications_endpoint` в `app_config.json` должен обслуживать выбранные вакансии.

## Запрос

POST по HTTPS, перенаправления отключены.

- `Authorization: Bearer <Firebase ID token>`
- `Idempotency-Key: <UUID>` — постоянный для пары пользователь/вакансия на этом устройстве.
- `Content-Type: application/json`

```json
{
  "job_id": "jobs:0",
  "resume": {
    "name": "Имя", "phone": "+77010000000", "salary": "150000",
    "city": "Алматы", "experience": "Опыт", "education": "Образование", "skills": "Навыки"
  }
}
```

Фотография и локальный URI не отправляются. Текст опыта ограничен клиентом, но сервер должен сам проверять все поля и длины. Подтверждение перед отправкой показывает пользователю, какие сведения передаются.

## Подтверждение

Только после надёжного сохранения и принятия заявки сервис возвращает HTTP 2xx:

```json
{"application_id":"server-generated-id","status":"received"}
```

Также поддерживается `status: sent`. Пустой ответ, `success: true` без ID, `draft`, отсутствие сети и HTTP-ошибка не считаются доставкой. Тогда доступен повтор. Android показывает «Отправлено» и пояснение, что сервис подтвердил получение; это не означает, что работодатель прочитал заявку.

## Требования к реализации сервера

Проверяй Firebase ID token через Firebase Admin SDK и связывай заявку с uid из проверенного токена. Проверяй существование вакансии и возможность отклика. Не доверяй uid из тела запроса. Обрабатывай Idempotency-Key атомарно: повтор после таймаута должен возвращать тот же ID, а не создавать дубль. Доставку работодателю/CRM выполняй через надёжную очередь с повтором и отдельным статусом; сохраняй подтверждение только после принятия задачи.

Если повтор с тем же ключом содержит изменённое резюме, возвращай исходное подтверждение либо явную ошибку конфликта — не создавай второй отклик молча. Серверная защита от дублей должна действовать также между устройствами.

Нужны ограничения частоты, проверка размера запроса, правила доступа, сроки хранения и процедура удаления данных. Это контракт интеграции, не развёрнутый сервер и не подтверждение готовности к публичному запуску.
